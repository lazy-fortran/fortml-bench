# LightGBM validation-aware warm continuation

This lane checks the validation-aware `lightgbm_t%fit_warm_start` contract. An
independent NumPy replay computes the four weighted validation losses for the
one-feature Newton fixture, selects the best round, and applies patience two.
The release app then continues a one-tree prefix to four requested trees with
both restore-best and retain-all policies. It also checks malformed validation
transactionality and the explicit CUDA refusal.

| policy | best iteration | retained estimators | best validation loss | warm seconds |
|---|---:|---:|---:|---:|
| restore-best | 1 | 1 | 4.0500000000000000e+01 | recorded in CSV |
| retain-all | 1 | 3 | 4.0500000000000000e+01 | recorded in CSV |

The NumPy and Fortran losses agree to zero at displayed precision. A malformed
three-row validation target returns `FORTNUM_DOMAIN_ERROR` (1) and leaves the
one-tree prefix prediction unchanged. CUDA prediction returns
`FORTNUM_NOT_IMPLEMENTED` (3); no host fallback is counted as GPU execution.

Raw rows are in [`lightgbm_validation_warm_start.csv`](lightgbm_validation_warm_start.csv),
generated by [`scripts/bench_lightgbm_validation_warm_start.py`](../scripts/bench_lightgbm_validation_warm_start.py).

Reproduce with:

```bash
python -B scripts/bench_lightgbm_validation_warm_start.py \
  --fortml ../fortml --output results/lightgbm_validation_warm_start.csv
```

This is CPU correctness and continuation evidence, not resident CUDA
performance evidence. The bounded LightGBM histogram path retains its typed
CUDA boundary.

FortML revision and benchmark provenance are recorded in every CSV row.
